# Source-checked memory reads: bounded reuse inside one transaction

Research date: 2026-10-28. Inspected checkout `/Users/alsoleg/.codex/worktrees/shared-memory-return/ai-knot`, HEAD `48b99d549bf8610dba8ecb047789033b1dc3a88c`. ## Current path

`docs/task-snapshot.md` correctly limits its promise to an all-or-error output; it explicitly leaves scanning and inherited-source SQL unbounded. `context.py:46–58` loads a namespace, then validates each eligible fact separately. `memory.py:266–369` reloads that fact, its slot peers, ACL grants, exact lineage roots/dependencies and their freshness records. Shared slot peers cause repeated grant reads; derived facts can load a root once for lineage and again for freshness. `_views(refs)` currently loops `_view`, so passing a larger tuple alone does not batch storage work. These are code observations, not latency measurements.

## Three applicable findings

1. **Use a read-operation cache whose lifetime is exactly the existing read-only transaction.** PostgreSQL reads already use `REPEATABLE READ READ ONLY` (`postgres_storage.py:338–358`): all statements see the snapshot established by the first relevant statement; read committed instead takes a new snapshot per statement. SQLite uses explicit `BEGIN` with WAL (`sqlite_storage.py:226–248`, initialization at 171–174); its read snapshot persists until the transaction ends. Reusing a grants set, facts keyed by `(namespace, id)`, complete slot lists keyed by `(namespace, slot_key)`, and freshness rows keyed by `(namespace, subject_kind, subject_key)` therefore adds no new cross-request staleness window. Capture the operation's `now` once as today. Seed maps from namespace rows already loaded, including empty/missing results when known. Keep them owned by this read and discard them at exit. [PostgreSQL 16 isolation documentation, accessed 2026-10-28](https://www.postgresql.org/docs/16/transaction-iso.html#XACT-REPEATABLE-READ); [SQLite transaction documentation, updated 2026-02-18, accessed 2026-10-28](https://sqlite.org/lang_transaction.html#read_transactions_versus_write_transactions).

2. **Deduplicate validation inputs before adding new machinery.** DataLoader's primary reference implementation memoizes repeated keys within a request, warns against sharing instances across users, and requires batch results to preserve key correspondence and missing entries. Transfer those rules as ordinary Python maps; the asynchronous JavaScript scheduler and an extra dependency do not help this synchronous path. Reuse the scanned fact rather than fetching it again; compute readable/current slot state once per unique slot; union exact root/dependency keys and reuse their rows/policies across descendants. Keep existing revision comparisons, unreadable-root handling, malformed-lineage rejection and freshness evaluation. If remaining distinct lookups dominate measured cost, a bounded bulk fetch is the next step. Batch acquisition must still yield a separate admission result for every fact: one rejected ref must not reject the whole corpus or disappear as an omitted batch row. [DataLoader README, main, accessed 2026-10-28](https://github.com/graphql/dataloader#caching-per-request); [batch function contract](https://github.com/graphql/dataloader#batch-function).

3. **Keep revocation boundaries and rechecks explicit.** A transaction may legitimately return its earlier snapshot after a concurrent revocation; a fresh operation must read fresh grants/source revisions. Never carry admission caches into another request, `review_context`, `begin_action`, or across the semantic embedding await: `semantic.py:108–119` and `206–220` intentionally use two reads. Cache views only for one reader, one `now`, one freshness mode and one read snapshot; cache raw rows by namespaced identity, not acceptance by fact ID alone. Do not install an uninvalidated cache in write sessions, where the same transaction may change facts/policies. OpenFGA independently documents that its enabled latency cache may miss an immediately preceding permission change; bypassing it queries storage. Its Batch Check coalesces combinations into one request, but that alone does not establish ai-knot's source/freshness contract. Transfer batching, not a TTL permission cache or a new authorization service. [OpenFGA consistency documentation, accessed 2026-10-28](https://openfga.dev/docs/interacting/consistency); [Batch Check documentation, accessed 2026-10-28](https://openfga.dev/docs/interacting/relationship-queries#batch-check).

## What this does not solve

Request reuse reduces duplicate work; it does not bound retained namespace size, prove completeness for a decision, improve semantic relevance, or erase already delivered text. Do not hold the database read open through model/network work: SQLite documents that long reads can prevent WAL checkpoint progress. Eagerly loading both namespaces/policies may also increase work before an early overflow; choose lazy reuse or bulk preloading from measurements. Preserve all-or-error overflow, exclusion of inaccessible facts from budgets, namespaced refs and new-transaction pre-action guards. No graph, new database, persistent cache, API expansion or performance claim is warranted by these sources. [SQLite WAL documentation, accessed 2026-10-28](https://sqlite.org/wal.html#concurrency).

Suggested focused validation: output/error equivalence on both backends; SQL counts across facts sharing slots/roots; source deletion/change, ACL revoke and freshness expiry between successive reads; concurrent revoke during a read retains current snapshot semantics; identical IDs across namespaces and negative lookups remain distinct.
