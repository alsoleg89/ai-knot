# Evaluation method for continued team coding work

Date: 2026-10-29. This is a research recommendation, not a result or a completed preregistration. It uses primary sources and reads only the existing evaluation summary, required-context documentation, and team-repository protocol, runner and sandbox. No fresh cases, hidden contracts, provider calls or execution results were inspected.

## What the evidence supports

**Task outcome and memory quality are different measurements.** SWE-bench evaluates generated changes by executing repository tests; Verified additionally distinguishes resolving the new issue from preserving existing behavior, and screens for underspecified requests and tests that reject valid solutions. LongMemEval separately measures retrieved evidence and final answers, explicitly observing that correct retrieval need not produce correct answers. These support executable contracts as the primary outcome and evidence coverage as a separate diagnostic; they do not establish that this project's memory improves coding. [SWE-bench evaluation guide](https://www.swebench.com/SWE-bench/guides/evaluation/), [SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/), [LongMemEval, §§3.3, 5.5](https://arxiv.org/html/2410.10813v2).

**Incremental history matters.** MemoryAgentBench feeds chronological chunks into accumulating memory and compares memory, retrieval and full-context methods using standardized prompts. It also reports compute-matched ablations rather than treating accuracy alone as sufficient. Its tasks are not a proof about repository editing or asynchronous agents. [MemoryAgentBench, §§3.3, Appendix J](https://arxiv.org/html/2507.05257v4).

**Successful output does not certify coordination.** MAST distinguishes loss of history, conversation reset, information withholding, ignored input and incorrect verification; it observes failures even in successful traces. Anthropic's long-running-agent report describes fresh sessions recovering progress through persistent artifacts, while leaving the relative merits of multi-agent architectures open. Use these as reasons to inspect transitions, not as causal evidence that any particular memory implementation helps. [MAST, Appendix A and I](https://arxiv.org/html/2503.13657v3), [Anthropic engineering report](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents).

**Cost and repetition change the claim.** AI Agents That Matter recommends cost-controlled, reproducible evaluations and adequate holdouts. τ-bench distinguishes success in any of several independent trials from reliability across all trials. Two repair attempts within one evolving trajectory and three dependent stages are not independent repeated runs. [AI Agents That Matter, §§2, 5–6](https://arxiv.org/html/2407.01502), [τ-bench, §3](https://arxiv.org/html/2406.12045v1).

## Minimum gates before a paid primary run

The following are recommendations derived from those sources and the inspected harness, not externally proven guarantees.

1. **Freeze independent fixtures and runtime.** Record three case identities, three stages each, public inputs, private contracts/references, model settings, code/image hashes, author exposure, selection rule, arm order, budgets and failure policy before results. Keep authorship separate from generic runner work. Validate that public requirements suffice, references pass, starters fail, and prior-stage solutions fail the intended changed requirement. Retain regression checks for unchanged obligations. A reference passing alone cannot show that a contract accepts other valid solutions. Authoring new tasks reduces exposure to these exact fixtures; it cannot certify absence of training contamination or human design bias.
2. **Preserve an actual continuation.** Apply only source additions, revisions and withdrawals between stages. Retain each arm's own code, failures, receipts, intent identity, checkpoint basis and action history. The event producer must not clear the executor's evidence basis, replace its candidate, or reconstruct a clean intent. Record pre-update, post-update and post-resume state so ordinary resume/invalidation handles stale work visibly. Restart with a fresh worker using durable state and no inherited conversation. This tests planned stage-boundary restart; crash recovery at arbitrary action boundaries requires separate evidence.
3. **Freeze common knowledge once.** Form each common researcher output from public stage information before coder arms, without their candidates or receipts. Save its exact text, basis, request and usage. When two arms expose the same evidence set, require the same ordered rendered entries, metadata and citation indices. Verify both set and byte equality; deterministic storage order alone is insufficient. Own code and feedback may diverge after treatment, so subsequent entire prompts need not match across arms.
4. **Keep the information boundary honest.** Never expose hidden tests, references, expected answers, answer-location labels or private case metadata to researcher/coder acquisition. Bounded test names/counts are an intentional feedback channel: freeze them equally and retain them in the transcript. If using `required_refs`, obtain them through the same documented public host policy for every applicable arm; hidden obligation labels would be oracle assistance. The helper preserves a known AND set; it does not discover completeness ([required-context contract](../required-context.md)).
5. **Account for all work.** Keep the same coder model/settings, attempt ceilings, output limits, context representation and sandbox feedback. Charge each consuming standalone arm the full common formation cost; count the shared call once in account totals. Include retrieval/embedding, invalid proposals, retries, refused acquisitions and conservatively reserved unknown usage. Publish actual calls/tokens and budget exhaustion alongside quality. Equal ceilings are a bounded-policy comparison, not equal actual compute or equal-cost optimization. Preflight full-history size or preregister overflow as acquisition failure; never silently truncate it.
6. **Gate executable validity.** Use the existing Docker sandbox and frozen contracts for every accepted proposal. Keep malformed/incomplete receipts, skips, timeouts and infrastructure failures visible and distinguish them from ordinary assertion failure. Preserve all candidates and charges even after failed attempts. The existing same-interpreter grader is not adversarial attestation; Docker isolation does not prove the generated program cannot tamper with grading.
7. **Make PostgreSQL an exact replay check.** SQLite is the paid primary trajectory. Replay recorded responses on PostgreSQL only after exact matching of the model-visible request, schema, generation settings and requested limits, with explicit normalization limited to irrelevant transport fields. Fail at the first mismatch, missing/extra call or divergent context; never substitute the next response to keep replay moving. Compare selection, restart/admission transitions, candidate hashes, receipts and accounting. Record logical replay usage separately from zero new provider spend. A matched replay supports backend behavioral parity on this trace; it is not an independent quality run or evidence of a database-caused quality advantage.

## Comparisons to preregister

| Comparison | Question and permitted interpretation |
| --- | --- |
| `task_memory` vs `current_docs_handoff` (primary) | Added value of acquisition/retention beyond the same current documents and frozen researcher output. If the ordered knowledge is identical and no acquisition pressure occurs, this is primarily an equivalence/control check; it offers little opportunity to identify selection benefit. |
| `current_docs_handoff` vs `direct_sources` | Value and cost of the common researcher output. Direct sources legitimately avoid formation cost. |
| `task_memory` vs `raw_team_history` | Bounded current acquisition versus accumulated revisions; report stale-context and overflow effects separately from code failure. |
| PostgreSQL replay vs SQLite recording | Deterministic backend compatibility, outside the quality ranking. |

Freeze the primary endpoint as **repositories passing every stage contract, out of three**; also report final-stage success out of three, all nine stage outcomes, first/second attempt outcomes, refusals, stale-basis detections, source/context fingerprints and cost. Final success must not erase an earlier failure. Trace diagnostics may identify missing evidence, stale evidence, ignored supplied evidence, invalid proposals and code errors; do not infer a unique root cause from pass/fail alone or add a default paid judge.

Preregister the number of independent paid repetitions and stopping rule; retain every run, including negative results. If only one is affordable, label it an exploratory paired case series. Additional runs with the same frozen handoffs estimate coder variability conditional on those handoffs; they do not estimate researcher variability. Nine stages and hundreds of assertions do not become nine or hundreds of independent repository samples. With three authored cases, report counts and per-case paired differences; avoid significance or general reliability claims. Even binomial intervals require appropriate sampling assumptions and are especially uncertain for small samples ([NIST interval guidance](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)).

Three short single-file tasks can demonstrate bounded continued editing and planned handoff/restart under changing sources. They cannot establish performance on existing production repositories, concurrent coordination, arbitrary crash recovery, long-horizon stability, semantic retrieval quality when fallback never runs, or a product-wide memory advantage. Do not revise defaults from this study alone.
