# Optimistic task-context guard

Researched **2026-10-28** against **`a12d71375eaecb0f956698569bc455b584955630`**. Official documentation retrieved today; PostgreSQL's current documentation identifies version 18. This note is source review and design inference: no SQL, tests, provider calls or model-quality experiments were run. It extends [growing task memory](2026-10-28-growing-task-memory.md).

## Assessment

A bounded, content-free guard can close the gap between selecting context and saving a proposed step. Compare the **entire admissible task revision set** again inside checkpoint's existing locked write transaction; let a caller explicitly pass the same guard at `begin_action` to extend that check to permit creation. This detects an added unselected condition without returning it to the model or introducing a schema, graph, service or persistent generation counter. It proves equality of two admitted sets at their validation times; it does not prove that a selected subset contained every prerequisite.

## Primary-source facts

| Source | Relevant documented behavior |
|---|---|
| [SQLite isolation](https://www.sqlite.org/isolation.html) and [transactions](https://www.sqlite.org/lang_transaction.html) | SQLite permits one writer. WAL readers retain their earlier snapshot. `BEGIN IMMEDIATE` starts a write transaction immediately and blocks other writers; acquisition can fail busy. |
| [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) | A phantom is a changed result set for a repeated predicate query. Read Committed uses a fresh snapshot per statement. Repeatable Read retains one snapshot and can still permit serialization anomalies. Serializable monitors predicate dependencies and may abort transactions, requiring whole-transaction retry. |
| [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html) | Row locks cover returned rows. Advisory locks rely on application cooperation; transaction advisory locks release at transaction end. Consistent lock ordering helps avoid deadlocks. |
| [PostgreSQL application consistency](https://www.postgresql.org/docs/current/applevel-consistency.html) | Explicit-lock consistency checks should use Read Committed, or obtain locks before a Repeatable Read snapshot is frozen. A snapshot predating lock acquisition can omit changes committed before acquisition finishes. |
| [SQLAlchemy version counters](https://docs.sqlalchemy.org/en/20/orm/versioning.html) | Its optimistic update includes the previously observed row version in `WHERE` and requires exactly one matching row. This detects stale versions of that row. |

## Confirmed code boundaries

- [`task_sources`](../../src/ai_knot/always_on/context.py) already defines the applicable universe: owner and, for a durable pool, `__shared__`; generic or exact-task non-episodic facts; supported/active state; exact current slot, ACL, lineage and freshness validation. Reuse this admission path rather than a second approximate SQL predicate. Off-task slot peers and referenced roots can affect admission even when they are absent from output.
- [`evidence_revision`](../../src/ai_knot/always_on/changes.py) hashes content, task qualifiers, validity, support and visibility fields. It excludes telemetry and the separate freshness-policy rows. ACL grant rows are separate too.
- [`SemanticContext`](../../src/ai_knot/always_on/semantic.py) releases its snapshot before embedding I/O and afterward revalidates captured sources. It does not discover every newly added candidate. [`checkpoint`](../../src/ai_knot/always_on/memory.py) currently validates supplied basis and saves through an intent revision CAS; that revision does not version task memory.
- [`plan_once`](../../examples/always_on_team.py) compares whole snapshots after model I/O, but its last snapshot and checkpoint use separate transactions. A write in that interval is not covered by the comparison.
- [`_intent_transaction`](../../src/ai_knot/always_on/memory.py) locks the owner, explicit extra namespaces and discovered evidence dependencies, rechecking scope expansion. Shared memory need not be locked when an existing intent/basis contains no shared dependency. `_transaction` adds shared scope automatically only for reads with an attached pool.
- [`SQLiteStorage`](../../src/ai_knot/storage/sqlite_storage.py) uses `BEGIN IMMEDIATE` for writes. [`PostgresStorage`](../../src/ai_knot/storage/postgres_storage.py) acquires sorted namespace advisory locks for writes and uses Repeatable Read for reads. Its write isolation is inherited from connection/server defaults. Storage fact replacement, durable [pool publication](../../src/ai_knot/pool.py), ACL mutation and [freshness updates](../../src/ai_knot/always_on/memory.py) acquire the relevant source namespace lock.

## Minimum viable contract — design inference

1. `task_guard(task_key, max_facts=128)` validates the normal task label/count limits and returns an immutable `TaskContextGuard(task_key, digest, max_facts)`. Hash a canonical, domain/version-tagged envelope containing owner, task admission identity (task key and applicable scopes), count policy and sorted exact `(namespace, fact_id, revision)` tuples. Return neither facts nor refs. Allow an empty admitted set. Fail explicitly above the limit; never hash a truncated prefix. The cap bounds admitted refs, not all scanning/decoding or database/network work.
2. Capture the guard **before context acquisition/model I/O**, or capture it from the exact acquisition snapshot. Capturing it after selection can bless a new condition the selector never saw. Separate earlier capture can cause conservative rejection if acquisition sees a newer set; normal chosen-ref validation must still run.
3. Optional `checkpoint(context_guard=guard)` adds **all current `task_scopes(memory)`** through `_intent_transaction(..., extra_namespaces=...)`, regardless of selected basis. Keep existing owner/workspace/dependency locks. Recompute using the yielded session and a single current `now`, then compare before any state mutation. Do not call the public guard reader from inside checkpoint: that would open another transaction. Mismatch or newly excessive candidate count fails closed without saving progress; document the error consistently. Existing lease, expected revision, state and basis checks remain required.
4. Optional `begin_action(context_guard=guard)` repeats the same locked set check before starting the action. The caller must explicitly pass it again: no automatic guard persistence or intent/task association is implied. On mismatch, follow existing basis-rejection behavior: persist a blocked intent with the existing `changed` reason, retain the prepared action, then raise `StaleEvidence` after transaction exit. Checkpoint mismatch instead rolls back without a state change. The host remains responsible for using the correct task label for its intent.
5. For PostgreSQL, explicitly establish **Read Committed writes before the first advisory-lock `SELECT`**, for example with `SET TRANSACTION ISOLATION LEVEL READ COMMITTED` as the write branch's first statement. The baseline inherits server/DSN defaults. Risk inference, not a reproduced failure: a lock-acquiring `SELECT` can establish a Repeatable Read snapshot before waiting, so a later guard read could miss the prior writer's committed addition. [PostgreSQL's official consistency guidance](https://www.postgresql.org/docs/current/applevel-consistency.html#NON-SERIALIZABLE-CONSISTENCY) explains this snapshot-before-lock problem. Include a regression with a Repeatable Read connection default and a coordinated writer. Advisory locks cannot protect against direct SQL writers ignoring the namespace convention.
6. State the guarantee as: “the admitted exact revision set at this guarded transition's validation equals the captured set.” Additions, deletions, slot conflicts/replacements, revocations, lineage/freshness changes and clock expiry are rejected **when they change that set or an included evidence revision**. Policy/grant edits that leave admission unchanged are outside that claim. Changing and restoring the exact set between reads (ABA) is also invisible. A digest is an optimistic comparison token, not a signed authorization capability or persistent history marker.

Locks prevent participating database writers from changing the predicate inputs during validation/save. They cannot stop time: active/freshness admission is evaluated at captured `now`, rather than continuously through commit. Keep the transaction short and free of model I/O. A guard passed only to checkpoint does not cover a subsequent action. Passing it again to `begin_action` checks the intervening interval, while changes after permit validation remain outside the guarantee. Existing [`begin_action`](../../src/ai_knot/always_on/_state.py) basis/lease checks remain required.

## Existing simpler alternatives

| Alternative | What it covers and leaves open |
|---|---|
| Whole `task_snapshot` before/after | Already available for small corpora; returns all facts or overflow. Current separate-read comparison leaves the final checkpoint interval open. An in-transaction comparison needs the same predicate/locking contract as the guard. |
| `review_context` / checkpoint all known refs | Existing exact-reference checks detect changes to supplied facts. Neither selected refs nor all previously known refs identify a new row. Intent CAS protects concurrent intent updates only. |
| Existing namespace change-stream heads | Potentially cheaper but coarser: unrelated task changes cause rejection; all admission-affecting writes need audited event coverage. Clock expiry changes no sequence. This would be a different contract. |
| Hold the original transaction through model I/O | Avoids a separate optimistic window only with suitable write/predicate protection; lengthens database lock ownership across slow external I/O. The guard keeps external work outside transactions. |
| Switch everything to Serializable | Adds backend-wide isolation/retry obligations. It does not connect model work performed between two separately committed transactions; the cross-transaction equality token is still needed for that purpose. |

## Unproven hypotheses and validation targets

The guard should prevent persisting a proposal across an observed newly admitted blocker. Better planning accuracy, adequate prerequisite selection, acceptable contention on a hot shared namespace and net latency/cost gains remain unmeasured hypotheses. It does not solve growth beyond 128 admitted facts, compaction fidelity or semantic completeness.

Minimum behavioral cases: unchanged and empty sets; new unselected private/shared/generic conditions with empty/private-only basis; deletion/replacement and same-slot conflict; ACL grant/revoke; freshness-policy/clock admission transitions; derived-root change; overflow before capture and during I/O; mutation immediately before checkpoint lock acquisition; checkpoint mismatch leaving intent revision/progress unchanged; explicit repeated guard at `begin_action`, which blocks on an intervening addition without starting the action; unchanged telemetry/off-task rows; invalid guard/count input and owner/task substitution. Include a separate PostgreSQL connection/isolation check and a coordinated competing writer. Policy edits with unchanged membership and ABA should follow the documented narrow contract rather than tests claiming stronger detection.
