# Память нескольких always-on агентов: границы знания и исполнения

Дата исследования: 2026-10-27. Внешние источники — официальная документация, официальный исходный код и научная публикация. Документ разделяет **документированную семантику источников** и **предлагаемую архитектуру AI Knot**. Последняя требует проверки реализацией; наличие похожего API у другого проекта не доказывает корректность AI Knot. Исследование не предполагает публикацию отложенного релиза.

## Главный вывод

Общая память полезна для обмена знаниями, но для нескольких постоянно работающих агентов необходимо отдельно определить: кто наблюдал факт, кто вправе его подтвердить, кому принадлежит задача и кто может изменить внешний ресурс. Общий semantic search не отвечает на последние два вопроса. Рекомендуемая исходная конструкция — одна согласованная база с разными областями личного состояния, общих знаний и координации действий; полноценный новый оркестратор для этого не обязателен. Это архитектурный вывод настоящего исследования, а не обещание прироста accuracy.

Различать нужно четыре идентификатора:

- `workspace_id` — проект/команда и граница доступа к общей памяти;
- `agent_id` — долговременная логическая личность и полномочия агента;
- `worker_id` — конкретный процесс/реплика, который может погибнуть или смениться;
- `operation_key` — одна бизнес-операция независимо от того, какой агент и какая попытка её выполняют.

Два worker одного агента — задача отказоустойчивого исполнения. Два разных агента, которые независимо решили задеплоить один сервис, — задача согласования намерений и доступа к ресурсу. Одинаковая схема памяти автоматически не делает эти задачи одинаковыми.

Но область их гарантий уже, чем «вся команда агентов»:

| Проверка | Наблюдение на текущем коде | Значение для нескольких агентов |
|---|---|---|
| Два owner создают одинаковый `client_key`, действие и request | Выдано **2 permit**, **2 разных idempotency key** | Идемпотентность действует внутри owner/intent. Общая бизнес-операция между разными агентами не дедуплицируется |

| Два owner одновременно проверяют один общий subject | **2 provider call**, **2 reservation**, **1 commit**, статусы `conflict`/`completed` | CAS защищает запись, но оплачиваются оба вызова. Нет общего claim до вызова |
| Два pool instance стартуют с одним snapshot, затем каждый публикует факт | В trust events **2 publish**, в persisted `publish_count` остаётся только `operator: 1` | Реальная потеря обновления snapshot статистики между экземплярами; сами факты и оба события в этом опыте сохранились |

Причины видны непосредственно в коде:

- [state_storage.py](../../src/ai_knot/always_on/state_storage.py): уникальность intent — `(owner, client_key)`, action — `(owner, intent_id, action_key)`; freshness — `(namespace, subject_kind, subject_key)` без owner политики.
- [memory.py](../../src/ai_knot/always_on/memory.py), `prepare_action` / `begin_action`, и [_state.py](../../src/ai_knot/always_on/_state.py): action key строится из owner, intent и action key; guard получает действия текущего intent.
- [maintenance.py](../../src/ai_knot/always_on/maintenance.py): ключ maintenance run — `(owner, run_key)`; проверка snapshot/revision после provider не объединяет вызовы разных owner.
- [pool.py](../../src/ai_knot/pool.py), `_stats_snapshot` / `flush_stats`: process-local словари записываются как целый snapshot. Последовательные flush двух уже созданных экземпляров достаточно воспроизводят потерю, одновременные SQL-записи не обязательны.
- [subscriptions.py](../../src/ai_knot/always_on/subscriptions.py): cursors/receipts относятся к owner, а poll использует транзакции и namespace locks. Это основа доставки, а не готовое распределение задач между разными logical agents.

Первые четыре случая показывают границы текущего контракта, а не автоматически нарушение обещанной per-intent безопасности. В опыте с permit внешний deploy **не выполнялся**: выдача двух разрешений ещё не доказывает два внешних эффекта. Изменение freshness показано в доверенном Python host; оно выявляет отсутствие разделения authority, но само по себе не доказывает удалённый обход аутентификации.

Воспроизведение: [multi_always_on_probe.py](multi_always_on_probe.py), сохранённый [результат JSON](multi_always_on_probe.json). Запуск из корня репозитория после установки проекта:

```sh
python docs/research/multi_always_on_probe.py
```

Использована настоящая **SQLite**, Python 3.12, две логические личности и несколько pool instances. Async-барьер обеспечивает пересечение provider calls. Время явно фиксировано во всех Fact и facade; внешний embedding/provider не вызывается. Это диагностический probe, **не** PostgreSQL/multiprocess нагрузочный тест. Перенос выводов на PostgreSQL основан на общем коде и ключах схемы; такой backend нужно проверять отдельно.

Текущий shared namespace — `__shared__` в выбранной БД/схеме; строка `team:ops` задаёт scope доступа к фактам, но не создаёт полноценный workspace. HTTP/MCP также нельзя считать готовым маршрутизатором произвольных owner: конфигурация задаёт личность сервиса, а доступ к pool требует подключения host. При недоверенных клиентах agent/workspace назначает сервер после аутентификации, не пользовательский JSON. Python ACL предполагают доверенный host; выдача прямых DB credentials позволяет обойти библиотечный слой.

## Что подтверждают первоисточники

### LangGraph: состояние выполнения и общие знания имеют разные области жизни

LangGraph явно разделяет checkpointer, сохраняющий состояние одного thread, и Store для долговременных данных вне графа, доступных разным threads. Их разрешено использовать совместно. Checkpointer нужен для продолжения и восстановления выполнения; Store — для фактов, предпочтений и общих знаний. RAM-реализация теряет состояние после рестарта. [Документация persistence](https://docs.langchain.com/oss/python/langgraph/persistence).

Store адресует запись парой `(namespace, key)`; namespace — произвольный tuple, а не обязательно пользователь. Документация рекомендует persistent backend для production и предупреждает, что поиск по namespace использует prefix, ограничивает число результатов и может иметь различный порядок в разных backend. [Документация Stores](https://docs.langchain.com/oss/python/langgraph/stores).

**Перенос в AI Knot:** отдельная область рабочего состояния каждого агента/запуска, отдельная область знаний проекта. Передача факта между агентами не должна переносить чужой незавершённый план или право исполнения. Namespace нужно сделать явной частью server-side authorization: из tuple адреса нельзя выводить наличие ACL. Поиск с prefix особенно нельзя использовать как разрешение читать все дочерние области.

### Letta: общий контекст бывает с разной семантикой конкурентной записи

В разделе **V1 SDK (legacy)** Letta memory blocks могут подключаться нескольким агентам. Документация прямо говорит: присваивание `value` полностью заменяет блок; при конкурентных изменениях побеждает последняя запись и затирает предыдущие. Предлагаемые ограничения — read-only блоки и контролируемая полная замена. [Memory blocks, раздел Modifying a block](https://docs.letta.com/v1-sdk/memory/memory-blocks).

Текущая Letta отдельно описывает agent как постоянную identity с собственной памятью, конфигурацией и историей. Разные conversations одного agent используют общую память; отдельные agents нужны для независимых identities/памяти. Это важное различие между несколькими задачами одного агента и несколькими агентами. [Stateful agents](https://docs.letta.com/concepts/stateful-agents).

Текущий официальный исходник Letta Code описывает shared memory как принадлежащий организации git-репозиторий, подключаемый нескольким агентам. Harness отправляет чистые commits после turn; при столкновении push делает pull с rebase и одну повторную попытку. Dirty files и конфликты автоматически не исправляются: агент получает напоминание. [Официальный исходник managing-shared-memory](https://github.com/letta-ai/letta-code/blob/main/src/skills/builtin/managing-shared-memory/SKILL.md). SDK различает временное подключение repository к session и постоянное подключение к agent; эти API требуют cloud backend. [Manage shared memory](https://docs.letta.com/agent-sdk/repositories).

**Перенос в AI Knot:** явные shared/private области и версионированные документы полезны. Для счётчиков, task ownership, receipts, budgets и action state нужна атомарная структурная запись, а не совместная перезапись текста. Git удобен для инструкций и длинных артефактов с историей, но конфликт, отложенный до следующего turn, неприемлем как механизм допуска внешнего действия. Legacy blocks и текущие git repositories нельзя смешивать в одну гарантию «Letta решает конкурентную память».

### PostgreSQL: транзакционный lock имеет ограниченную область действия

PostgreSQL определяет advisory locks как соглашение приложения: СУБД не заставляет все клиенты его соблюдать. Transaction-level advisory lock освобождается в конце транзакции; session-level — явно либо при закрытии session. Для нескольких объектов рекомендуется единый порядок захвата, а долгие транзакции создают проблемы ожидания. [PostgreSQL 16: Explicit Locking, разделы 13.3.4–13.3.5](https://www.postgresql.org/docs/16/explicit-locking.html).

**Перенос в AI Knot:** атомарная запись памяти и долговременное владение бизнес-ресурсом — разные механизмы. Namespace lock может защитить SQL mutation, но после commit не резервирует deploy target на время LLM/tool call. Для владения нужен persisted claim, срок, поколение владельца и проверяемые переходы состояния. При смене владельца старый worker не должен получить право записать результат только потому, что он когда-то держал lock. Вызов внешнего API выполняется вне долгой SQL-транзакции.

### Temporal: повторяемое выполнение требует защиты на стороне эффекта

Temporal документирует окно сбоя: Activity успела выполнить работу, но worker погиб до сообщения о завершении; Activity будет повторена. Наблюдаемое однократное завершение не означает однократный физический вызов. Idempotency keys проверяет вызываемый сервис, а не сама Activity. [Activity Definition, Idempotency и Activity retry policy](https://docs.temporal.io/activity-definition).

**Перенос в AI Knot:** ключ попытки/агента недостаточен, если два разных агента описали одну бизнес-операцию. Дедупликационный ключ должен переживать retry и handoff; отдельный `resource_key` должен предотвращать несовместимые операции над одним ресурсом. Для внешнего сервиса, поддерживающего conditional update/version, передавать и проверять соответствующий token. Если внешняя система не обеспечивает idempotency/conditional mutation, локальная память не может гарантировать ровно один эффект: неопределённый исход требует reconciliation перед повтором.

### Научная рамка: память — несколько компонентов, а не один индекс

CoALA описывает language agent через модульную память, действия с внутренней памятью и внешней средой, а также процесс выбора действий. Это полезная классификация для проектирования границ модулей; публикация не является доказательством точности конкретного multi-agent memory implementation. [Sumers et al., Cognitive Architectures for Language Agents, TMLR 2024](https://arxiv.org/abs/2309.02427).

**Перенос в AI Knot:** оценивать отдельно retrieval, консолидацию знаний и принятие решения об исполнении. Улучшение одного слоя не гарантирует улучшение остальных. Особенно важно не смешивать факт «агент сообщил об успехе» с подтверждением внешнего действия.

### Collaborative Memory: происхождение и текущие права нужны вместе

Работа Rezazadeh et al. описывает private/shared fragments с неизменяемым provenance: contributing agents, accessed resources и timestamps. Текущие отношения user–agent–resource определяют доступ к сохранённым фрагментам; read/write policies учитывают изменение прав. Это особенно близко к проблеме общей памяти нескольких пользователей и агентов. [Collaborative Memory, arXiv:2505.18279](https://arxiv.org/abs/2505.18279).

**Перенос в AI Knot:** provenance должен включать исходный ресурс, namespace и конкретную версию, а не только имя последнего пересказчика. Для производной записи проверяется выбранная политика доступа по lineage. Например, консервативное пересечение разрешений всех исходных материалов допустимо как начальная политика; это предложение, а не уже реализованная гарантия AI Knot. Если агент уже прочитал текст, отзыв права не удалит его из ранее переданного LLM-контекста; можно контролировать последующие выдачи/публикации и сохранённые производные записи.

## Предлагаемая модель для AI Knot

Все положения этого раздела — предложения, а не описание уже реализованных гарантий.

На уровне публичного продукта достаточно трёх областей: **личная память агента**, **знания workspace**, **работа workspace**. Таблица ниже раскрывает данные внутри этих областей; она не требует шести сервисов, отдельных БД или нового framework. Внутри библиотеки разумно расширить существующие SQL mutations/claims и оставить scheduler/tool execution в host.

| Область | Что хранить | Кто изменяет | Как согласовывать |
|---|---|---|---|
| Личная память agent | рабочие гипотезы, индивидуальные процедуры, долгосрочные предпочтения | соответствующий agent и явно уполномоченный администратор | revision/CAS; изоляция по identity |
| Состояние run | checkpoint, шаг, receipts, временный контекст | worker, владеющий актуальным claim | lease generation и проверка каждого перехода |
| Общие наблюдения | сообщения агентов и внешних источников, timestamp, provenance | разрешённые издатели | append-only записи; стабильный event ID |
| Подтверждённые знания | канонические значения, версии, сроки актуальности, основания | отдельное право подтверждения/коррекции | атомарный revision check, конфликт как данные |
| Координация | claims, business operation keys, resource ownership, общий бюджет | control plane с проверкой прав | уникальность/условные mutations в БД |
| Политики | источники истины, freshness, правила публикации и допуска | отдельная административная authority | версии и явная область действия |

### Общая память: публикация, подтверждение, инвалидирование

Агент публикует наблюдение с `origin`, `source_revision`, `observed_at`, `producer_agent_id` и областью видимости. Наблюдение ещё не становится истиной проекта. Право читать/предлагать наблюдение не должно подразумевать право менять источник истины, freshness policy или правила допуска действий.

Каноническая запись хранит lineage до исходного доказательства. При копировании agent A → summary B → shared memory C цепочка не должна теряться. Иначе три пересказа одного сообщения начинают выглядеть как три независимых подтверждения.

Иллюстрация математической ошибки: наивное объединение `1 − ∏(1 − pᵢ)` даёт `0.96` для двух чисел `p=0.8`. Эта формула описывает вероятность объединения независимых событий и сама по себе не является общей формулой posterior истинности утверждения. Если второе свидетельство — пересказ первого, нет и независимости: рост до `0.96` тем более не обоснован. Это пример, а не утверждение о текущей формуле AI Knot. Практическое начальное правило — группировать evidence по корневому источнику и не увеличивать уверенность от его копий. Более сложная модель корреляций имеет смысл только при измеримом выигрыше.

Производные summaries должны хранить зависимости от версий источников. Изменение/отзыв источника помечает зависимые записи как требующие обновления; оно не должно незаметно оставлять старое summary «подтверждённым». Тот же принцип применяется к изменению ACL: перестать выдавать материал из локального cache недостаточно, если производный текст продолжает раскрывать отозванный источник. Нужна заранее выбранная политика доступа к производным данным.

### Доставка событий и распределение работы

Логическим агентам нужны независимые durable cursors, если каждый обязан увидеть одно изменение знания. Нескольким worker одного логического агента нужен общий claim, если обработать изменение должен один из них. Один глобальный ack для всех агентов потеряет fan-out; отдельная очередь каждой реплики может продублировать работу. Это проектируемые delivery semantics, которые следует сделать явными в API.

`ack` означает завершение обработки конкретной доставки, но не владение задачей и не завершение внешней операции. Коммит canonical update и запись события о нём следует делать атомарно в существующей БД. Начальный вариант может использовать таблицу событий и receipts; отдельный брокер нужен только при доказанной нагрузке или требованиях к интеграции.

### Обслуживание памяти и цена постоянной работы

Дедупликация commit не устраняет дублирование дорогого provider call: два агента могут одновременно начать refresh одного subject. Claim на refresh следует получать **до** вызова провайдера, по области общего предмета и версии политики, а не только по agent/run. Claim на запрос пользователя и claim на обслуживание памяти — разные сущности с разными сроками.

Общий проектный бюджет нужен дополнительно к лимитам отдельных агентов. Иначе добавление N агентов умножает refresh/compaction работу, даже если все читают один источник. Минимальные меры: scoped dirty subjects, объединение повторных refresh, ограниченная конкуренция, jitter и отдельный бюджет обслуживания. В observability различать число provider calls, успешные commits, конфликты и повторные доставки.

Ключ общей единицы refresh можно начать с `(workspace, subject, evidence_revision, policy_revision, kind)`. Claim берётся до provider call, результат доступен подписанным агентам независимо. Объединять просто по тексту вопроса нельзя: разные права, версии или выбранный source могут требовать разных результатов. Workspace budget должен учитывать зарезервированные/фактические вызовы; конфликт commit не делает состоявшийся вызов бесплатным.

Для пробуждения агентов сначала достаточно durable events и целевых подписок на fact/slot. При измеренном расходе idle polling PostgreSQL `LISTEN/NOTIFY` может давать сигнал «появились данные»; source of truth остаются таблица событий и cursor. Регистрация LISTEN живёт в session; после reconnect порядок — LISTEN и commit, затем чтение backlog, затем ожидание сигналов. В payload не передавать приватные факты. [LISTEN](https://www.postgresql.org/docs/16/sql-listen.html), [NOTIFY](https://www.postgresql.org/docs/16/sql-notify.html). Это будущая оптимизация: текущий API предлагает poll, встроенного push wakeup здесь нет.

### Действия над одним внешним ресурсом

Перед стартом agent должен атомарно зарезервировать business operation и получить право на нужный resource. Новый claimant получает новую generation. Каждый локальный переход состояния проверяет её. Старый worker после истечения lease не может завершить запись от имени нового владельца.

Однако локальная проверка generation не останавливает уже отправленный сетевой запрос. Fencing работает на границе, где изменяется ресурс: внешний actuator должен отклонять старое поколение, либо внешняя система должна поддерживать собственную conditional mutation. При отсутствии такой возможности выбирать policy «unknown → reconcile», сохранять receipt/probe и запрещать слепой повтор опасного действия. Resource serialization и дедупликация одной операции нужны одновременно: разные допустимые операции над ресурсом тоже могут требовать порядка.

`operation_key` должен обозначать намеренную бизнес-операцию, а не hash payload: два одинаковых по сумме платежа могут быть разными легитимными операциями. Он сохраняется при handoff A → B. `resource_key` обозначает цель, например deployment окружения; generation монотонна в области этой цели. Нельзя заменять эти понятия случайным ID очередной попытки.

## Что можно использовать уже сейчас

1. **Один logical maintainer общей памяти.** Общие refresh запускает owner `workspace-maintainer`; его реплики используют одинаковый стабильный run key и provider configuration. Это переиспользует текущую owner-scoped дедупликацию maintenance. Maintainer получает только необходимые shared grants, а личные namespaces остальных агентов остаются их собственностью. Это организационный обход дублирования общих refresh, а не workspace-wide quota.
2. **Долгоживущий facade на agent и отдельные subscriptions.** Подписывать на нужные subjects, не на все изменения. Host сначала сохраняет результат обработки/receipt, затем делает ack; повторная доставка должна быть безопасной. Shared task можно вести отдельным host-owned координатором с worker IDs и существующими intent claims, не смешивая личную память всех агентов под одним owner. Host отвечает за авторизацию и связь worker с реальной личностью.
3. **Общий ключ бизнес-операции на границе host/API.** Передавать один внешний idempotency key между агентами и хранить общий результат в durable registry. Текущий ActionPermit сам не создаёт такой межагентный ключ. Пока targeted API не появилось, такую регистрацию реализует host; неизвестный результат сначала сверяется с внешней системой.
4. **Явная граница workspace.** Для первых независимых workspace можно использовать отдельные БД либо схемы с корректными role privileges. Один `search_path` не создаёт security boundary: PostgreSQL разрешает доступ в другие схемы при наличии прав. [Schemas and Privileges](https://www.postgresql.org/docs/16/ddl-schemas.html). Для сложной tenancy требуется отдельное проектирование авторизации, а не переименование namespace.

Для многопроцессного production-развёртывания естественно использовать имеющийся PostgreSQL backend; SQLite оставить для локального single-host режима и воспроизводимых проверок. Это не устраняет описанные выше owner/resource/statistics gaps.

## Минимальная программа проверки

Здесь критерии будущей реализации. Наличие существующих тестов одиночного агента не заменяет эти сценарии. Запускать для SQLite и PostgreSQL отдельными соединениями/процессами; барьеры должны обеспечивать нужное пересечение, а не надеяться на случайный timing.

| Сценарий | Проверяемый инвариант |
|---|---|
| Два агента обновляют разные поля одного общего объекта | Оба изменения сохраняются; stale whole-object overwrite отклонён |
| Два агента предлагают разные значения одного факта | Конфликт видим, provenance сохранён; порядок прихода не становится скрытым критерием истины |
| Два worker одного agent получают событие | Один актуальный claim; повторная доставка допустима и не дублирует logical processing |
| Два разных agent подписаны на одно изменение | Оба получают свою доставку и имеют независимые receipts |
| Два agent выбирают одну business operation | Один logical operation; согласованные idempotency key и результат |
| Разные операции выбирают один resource | Несовместимые исполнения не стартуют параллельно |
| Worker задержался, lease истёк, новый worker продолжил | Старый generation не меняет локальный state; отдельно проверен внешний fencing либо reconciliation |
| Внешний эффект выполнен, commit результата потерян | Состояние unknown не приводит к повторному эффекту без idempotency/reconciliation |
| Reader пытается изменить freshness/source policy | Отказ независимо от права чтения shared memory |
| Два agent одновременно обновляют один subject | Один дорогой refresh на claim; бюджет учитывает фактические calls |
| Один источник пересказали несколько agent | Число независимых подтверждений не растёт от копий |
| Source revision/ACL изменились после сборки контекста | Зависимые знания помечены; допуск действия перепроверен перед исполнением |
| Два процесса публикуют факты и статистику | Оба факта и оба durable counters сохранены; snapshot не затирает чужое обновление |

Для оценки accuracy нужен отдельный неизменяемый набор multi-agent traces: независимые наблюдения, противоречия, обновления источника, копирование одного evidence и устаревший контекст. Сравнивать одинаковые данные и суммарный бюджет вызовов; показывать retrieval precision, долю unsupported confirmations, stale-decision rate и duplicate-effect rate отдельно. До измерения нельзя утверждать, что общая память увеличивает точность.

Отдельные критерии always-on: в простое — ноль LLM calls; один shared subject при 100 одновременных запросах — один provider call на актуальную единицу refresh; 20 пересказов одного источника — одно независимое подтверждение. Измерять p50/p95 wake/recall latency, стоимость нового полезного знания, число конфликтов, долю лишних пробуждений и завершённые задачи. «Один provider call» требует нового общего claim; текущая owner-scoped реализация этот критерий не выполняет. Ровно один внешний эффект проверяется только с реальным контрактом удалённой идемпотентности/conditional update, а не одним счётчиком local permits.

## Рекомендуемый порядок

1. Зафиксировать server-side идентичности, workspace/tenant scope и отдельные права чтения, публикации, подтверждения и управления политикой.
2. Исправить воспроизведённую потерю counters между pool instances: атомарные SQL deltas либо транзакционная проекция событий вместо замены process-local snapshot. Публикация fact, событие и обновление проекции должны согласованно коммититься. Наличие текущего trust ledger само по себе не гарантирует восстановление после crash между отдельными записями.
3. Ввести/проверить business-operation дедупликацию, resource ownership и корректность takeover, затем external reconciliation.
4. Согласовать независимые subscription cursors и claims общего refresh до затратных вызовов.
5. После этого развивать provenance-aware консолидацию и измерять влияние на retrieval/decisions.

Ближайший полезный объём: counters, authority общей freshness policy, operation/resource coordination и claim общего refresh. Затем — lineage и инвалидирование производных знаний. Новая vector DB, отдельный message broker, обучение selector и новый orchestration framework не требуются для исправления воспроизведённых ограничений. Прирост accuracy остаётся измеряемой гипотезой; отсутствие дублей и потерянных обновлений проверяется отдельными инвариантами.
