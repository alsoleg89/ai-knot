# Bounded planning turn — independent pre-implementation review

2026-10-28; base `abe8be8`. Read the plan, existing `inspect_turn`/`acquire_missing_context`, memory facade claim/resume/checkpoint, and pure state transitions. Design/source review only; no provider/Keychain access, test or full-CI run, code changes or additional agents.

**Design is viable as an opt-in host recipe.** A bounded snapshot, one callback invocation and a persisted proposal address the missing path without changing inspection or pretending lexical acquisition proves requirement satisfaction. Reuse the existing claims, resume packets and checkpoints; no new state schema, lease API, worker framework or domain action oracle is needed. The following details should be explicit in implementation/tests.

1. **Guard pending actions independently of readiness.** `resume.pending_actions` includes PREPARED as well as STARTED/UNKNOWN, but PREPARED alone does not make `packet.ready` false or add `unknown_action`. Reject any pending action before claim, after claim and after callback. Otherwise the helper could replace proposal/basis while a prior prepared operation remains pending. Do not rely only on the inspection status or reason string.

2. **Use one precise plannability check at each boundary.** Before claiming, require no active lease and an eligible current state. After claiming, expect RUNNING/live_lease for this helper's own valid token, rather than requiring `packet.ready`. Permit a BLOCKED source-replan only when every blocking reason is in the known source-related allowlist; the presence of `stale_basis` must never override host_blocked, deadline, due verification or unknown effects. Preserve WAITING/terminal states. Use fresh `resume` to settle lease/deadline changes, and do not trust the earlier observation after an await.

3. **Keep proposal output from triggering its own inference.** Put all helper-owned attempt/proposal fields, including callback `data`, under one reserved progress key and exclude that entire key from the input fingerprint. Preserve host application progress separately. Merging callback data into fingerprinted application progress would cause a successful result to change its own input and defeat quiet deduplication. Do not fingerprint revision, lease, helper-written next_step or basis as incidental task state. Include all actual input semantics/selection arguments in a stable representation; current exact refs/text distinguish source updates. A later explicit host progress/trigger change legitimately permits another attempt. A single durable latest marker is ordinary suppression, not an exactly-once inference ledger.

4. **Cleanup must not acquire authority.** Use the revision from the most recent successfully guarded packet for checkpoint; if CAS fails, do not fetch a new revision and blindly retry the old decision/cleanup. Only the owned unexpired lease and still safely plannable intent may store a sanitized failed-attempt marker and clear an obsolete next_step/basis. For a newly manual-blocked intent, the current transition API does not generally allow checkpointing BLOCKED→BLOCKED merely to release a lease; checkpointing READY would clear the block. Leaving this helper's lease to expire is safer and does not require a new release API. Never cancel the task or clear another worker's lease for convenience. Cancellation must be re-raised after best-effort guarded cleanup; do not store exception text, raw malformed model output or secret-bearing diagnostics.

5. **Bound callback output before parsing.** The input cap and next_step cap do not bound arbitrary callback `data`. Apply a raw UTF-8 output cap before strict JSON parsing, reject duplicate keys/nonfinite values/deep-invalid JSON safely, and require exact integer citation types (`type(i) is int`, so JSON true is not citation 1). Keep the parser to this small response contract. The callback is trusted application code that owns actual aggregate provider/token metering; one local invocation reservation is not proof of one billable request. An asyncio timeout is cooperative: a callback that suppresses cancellation can outlive it. Recheck the lease/deadline and reject a late result; do not promise a hard wall-clock return bound.

The complete post-callback snapshot comparison should compare all admitted refs/text, not only chosen citations, so an added relevant fact or removed/revised/revoked/expired source observed there rejects the old proposal. Selected refs are checked again for checkpoint. This still is not an atomic completeness guarantee through checkpoint: source additions after that read are not covered by selected-basis validation. The plan already preserves action-time guards and acknowledges this boundary; keep that wording.

The callback replaces a scripted planning decision, not the application's domain validation. READY with valid current citations means a proposal has been persisted; unrelated citations or wrong application data can still produce a bad proposal. Keep domain validation and prepare/begin/finish action guards separate. A wait with no basis should remain an explicit bounded host timer, not an implicit successful decision.

For the planned smoke comparison, use the same domain validator, action guards, public output contract and invocation accounting in all arms; separate proposal creation, domain correctness and actual effect outcome. A current-task-bundle control is particularly important because any improvement could be caused by supplying the bundle or enabling a callback, rather than by a memory-specific benefit. Freeze example inputs and scoring before paid calls, preserve all failures, and make no general quality claim from these small inspected traces.

Ponytail: keep one serialized callback input, one strict response parser, one guard predicate and one best-effort cleanup path. These boundaries justify small helpers; a generalized planner/dispatcher or persistent retry service would be unnecessary.

The new scripted workflow demonstrates pending→wait/quiet→restart with confirmed observation→proposal→host policy/prepare/begin→unknown response→reconciliation→completion. Its callback is explicitly a fixture decision, and the effect/receipt are scripted, not a live connector outcome. The same application policy checks the current structured observations and proposal data before the effect. No model-created observation is published as truth; the model does not receive a lease or directly execute the operation. Both source facts have explicit times compatible with the example clock. The example should continue to be described as an executable protocol demonstration, not decision-accuracy or external-effect evidence.

One residual concurrency boundary was identified and accepted for documentation: `checkpoint` atomically rejects STARTED/UNKNOWN effects but permits PREPARED; `prepare_action` does not advance the intent revision. Another actor reusing the same token could therefore create a PREPARED action after the final host resume and before checkpoint without invalidating that CAS. This recipe requires an exclusive controller for its lease token; callback code must not share/reuse the token for concurrent operations. The no-await final synchronous section avoids ordinary same-loop interleaving but is not an atomic barrier against same-token threads/processes. Source additions after the final snapshot are similarly outside the snapshot comparison. Stronger atomic semantics would be a distinct library change, not something this host example proves. Parent agreed to state these limitations rather than expanding the public API.
